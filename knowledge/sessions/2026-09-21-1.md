## Q1 - When the tool finishes reading an engagement's documents, what should be sitting in the folder, and what do you do with it next?

*Asked because the build had stalled on it: all three shipped recipes end at `qc-tieout`,
nothing says what a version-1 run hands over, and I had assumed the answer needed the real
model's named ranges - which would have meant waiting for the file.*

**Answer.** "It won't go directly into the model - this is my plan. It will go into a
workbook that is layed out the exact same as the actual model - so I can just copy and
paste the data over. That is for version 1. So you can start building what you think the
layout of the model would be, and can tweak it later to match exactly."

**What this settles.**

1. The deliverable is a **separate workbook**, not the firm's model. Nothing this build
   produces is ever opened as the model or written into it.
2. Its layout **mirrors the model's** closely enough that a block can be copied from one
   and pasted into the other. Fidelity of *layout* is the requirement; there is no named
   range to bind and no template to pin.
3. The layout may be **guessed now and corrected later**. This is Caleb overruling the
   refusal recorded in `BUILD/OPEN.md` section 4d - and the refusal does not apply to what
   he is actually asking for. What was refused was binding a guessed template at
   `valuation/non-esop/_segment`, which would change what every non-ESOP run *writes into
   the firm's model* on a guess. This writes into a workbook of our own, so a wrong guess
   costs a re-layout and nothing else.

**What it unblocks.** B-033 (a version-1 recipe that stops at organised data) and B-034
(the input-help workbook) no longer wait on `Model Template - MASTER 2026`. The delivery
path, which has never executed on any run, gets something real to release.

## Q2 - When you copy and paste that data across, what exactly do you select?

*Asked to find out how exact the layout has to be: one block landing in one place needs
cell-for-cell geometry, a column at a time needs only the row order to line up.*

**Answer.** "For things like the input tab, it will be exactly the same. But for things
like the ws tab or income statement or balance sheet tab, if repeat client it would have
to get the structure from the old model, and make it match that. But if new, it would get
the structure from the model template. Or we can just build in the structure to its memory
for if it is a new client."

**What this settles - and it is bigger than the question asked.**

The workbook does not have one layout. It has two kinds of tab:

* **Input** - fixed, identical every time. One layout, built once.
* **WS, IS, BS** - **structure derived per engagement**:
  * *repeat client*: read the structure out of **last year's model** and match it
  * *new client*: from the model template, or a default built into the tool

So the deliverable is not a template with data poured into it. It is a workbook whose
shape is **computed from the engagement** - which is the same fact the fourth session
stated from the other side: for three quarters of the work *the prior workbook is the
chart of accounts*, not `taxonomy/`.

**Findings against the build.**

1. **B-034 is the wrong shape as written.** It proposes registering the input-help
   workbook as a template at `valuation/non-esop/_segment` with an input schema - one
   fixed structure. That is right for Input and wrong for WS, IS and BS, whose structure
   is per-engagement. Needs revising rather than building as specified.
2. **B-036 / P69 has found its caller.** `tools/rollforward.py` carries line items forward
   and is reached by nothing. This is what it is for. Its backlog note says the Excel half
   "needs the real template"; that is now known to be wrong - what it needs to read is the
   *client's own prior workbook*, not the firm's template.
3. **P79 supplies the input.** `prior_model` on the engagement is the path to last year's
   workbook, set at `/admin`, refused unless the file exists. It was built because the
   analyst asked for the field by name; this is the first thing that consumes it.
4. `needs_a_prior_model()` already answers "is this a repeat client and do we have last
   year's file" - which is exactly the branch above.

## Q3 - Which rows does the tool fill, and which are the model's own formulas?

*Asked as a safety question: a workbook that filled the calculated rows, pasted as a block,
would overwrite live formulas with hard numbers and not look wrong for months.*

**Answer.** "Subtotal rows are formulas, but it can be in the tool as well. I will just
copy over the hardcodes, the subtotals in the tool output are what makes me beleive
everything is done correctly, like if the balance sheet balances for example, or if the
net income matches what the client gave."

**What this settles.** The subtotals are not data. They are **the evidence**.

* The model's subtotal rows are formulas and stay formulas - he pastes only the hardcodes,
  so the hazard the question was about does not arise.
* The tool computes the subtotals **anyway**, and their whole purpose is to be *looked at*:
  the balance sheet balancing, net income agreeing with what the client stated. That is
  how he decides the extraction is right without going back to the PDF.

This is the fourth session's acceptance rule said from the other side. There, a figure was
trustworthy when "its totals all re-add and the statements tie". Here that check is not an
internal gate - it is **the visible output**, and it is what earns his belief.

**Findings against the build.**

1. **B-040's producer has its shape.** "Nothing sets `extracted` and `arithmetic_cover`"
   has been open since P67 because nothing mapped a passing check to the figures it
   covers. The mapping is the statement's own structure: a figure is covered by the
   subtotals it feeds, and the subtotal is covered when the computed value equals the one
   the client's document states. The tool already has both halves - the columns are read
   (P85) and `tools/statement_checks.py` computes balance-sheet-balances and
   net-income-ties - and nothing had joined them.
2. **B-028 has its surface.** "Say tie-out in the analyst's sense, or stop saying it": the
   analyst's tie-out is exactly these two checks, and this is where they belong - on the
   face of the deliverable, not in a scorecard.
3. **A layout requirement, new.** He copies *the hardcodes* and not the subtotals, so the
   workbook has to make the two obviously distinguishable - otherwise selecting them means
   picking non-contiguous ranges by eye on every tab.

## Q4 - When a subtotal does not match, do you still want the workbook?

*Asked because the two builds are very different: stop and escalate, which is how every
other guard here behaves, or deliver anyway with the bad rows marked.*

**Answer.** "Yes still want the workbook, just find and flag why it is not matching or
checking out."

**What this settles.**

* **The deliverable is not gated on the checks.** A failed tie is not a halt in version 1.
  This is a real departure from the rest of the build, and it is right for what version 1
  is: he is not running a model off this workbook, he is reading it and typing from it, so
  a workbook with one flagged section still saves the other two hours.
* **"Find why", not "flag that".** The requirement is a diagnosis, not a red mark. "The
  balance sheet is out by 4,000" is the beginning of the work, not the end of it.

**Why that is buildable rather than hopeful.** The tool now has what it needs to localise a
break deterministically, and most of it arrived in the last two days:

* both columns are read (P85), so *which year* breaks is knowable, and a year that ties
  beside one that does not is most of the answer
* the rows behind every total are in the parse store under their own locator, so the
  candidates for a missed or doubled row can be enumerated rather than guessed
* a difference equal to a row's value points at that row being dropped or counted twice;
  a difference divisible by nine is the classic transposed-digit signature, which is
  exactly the failure OCR produces
* `tools/statement_checks.py` already computes the two checks he names

**Finding.** This is the shape B-028 was asking for. "Tie-out" in the scorecard's sense is
footing; in the analyst's sense it is *the balance sheet balances and net income agrees*,
and those are the two he named unprompted. They belong on the face of the workbook with a
reason attached, not in an eval metric.

## Q5 - Are the tabs named the same in every client's workbook, and does the data start in the same place?

*Asked because for a repeat client everything hinges on reading last year's file. If every
model came off the same firm template the addresses are predictable; if models get lived
in, the tool has to find the block and say when it is unsure.*

**Answer.** "Yes the tabs are usually named the same in every workbook, and the data
usually starts in the same place. But ya sometimes people put stuff in the sales detail
tab, or make extra tabs to support the income statement or other things."

**What this settles.** Two *usuallys* and one named exception.

* The standard names and positions are the common path and can be the tool's first guess.
* They are not a guarantee. "Usually" is not "always", and a tool that assumed the address
  would silently read the wrong rows on the workbook where somebody inserted a note at the
  top - which is the failure this build keeps finding in other clothes.
* The exception has a shape: **extra tabs somebody added to support the income statement**,
  and material put into Sales Detail.

**What it means for the build.**

1. Look in the expected place first; **verify what was found** rather than trust the
   address. A tab called WS whose column A does not read like line items is a finding.
2. An unrecognised tab is not noise. It is somebody's working, supporting a statement the
   tool is about to reproduce - so it gets **reported**, not skipped silently. Version 1
   should say "this workbook has three tabs I did not recognise, named X, Y, Z" and leave
   what to do about them to a person.
3. This is the same rule the build already follows for a sheet the workbook reader skips:
   every skipped sheet is reported with a reason.

## Q6 - What is on the Sales Detail tab, and does version 1 need to fill it?

**Answer.** "The sales detail is specifically for the breakout of the sales/revenue tab.
It usually comes from client docs. But sometimes people include it in the ws tab. Just

**What this settles.**

* Sales Detail is the **revenue breakout**, the same idea as WS but for one line. It comes
  from client documents, so it **is** part of version 1's extraction rather than a working
  area to leave alone.
* **The same data can live in either tab.** Sometimes the sales breakout is in Sales
  Detail, sometimes somebody put it in WS. Which one is not a property of the firm's
  template - it is a property of *that client's* workbook.

**What it means for the build - and it deepens Q2.** I had recorded the prior model as
supplying the *row structure* of a tab. It supplies more than that: it decides **which tab
a kind of data belongs in at all**. So the rule is not "revenue breakout goes to Sales
Detail"; it is:

* **repeat client** - find where last year's model put the revenue breakout, and put it
  there. Look before deciding.
* **new client** - Sales Detail, which is the firm's own convention and is the default the
  tool should carry.

That is the third time the same shape has come up today: for a repeat client the prior
workbook is the specification, and the firm's convention is only the fallback. It is worth
stating once in the build rather than three times.

## Q7 - How do you decide this year's line is last year's row?

*Asked because it is the judgement that does the work for three quarters of engagements,
and it decides whether this is a matching problem code can do and show, or one the tool
should put in front of a person every time.*

**Answer.** "Is it close enough wording, and in the right ballpark for amount. And check to
see in last years client docs to see if the same numbers show up. Just to make sure they
categorized it the same. That's how I do it."

**What this settles.** A three-part test, and every part of it is checkable:

1. **wording close enough** - string comparison, normalised
2. **amount in the right ballpark** - arithmetic
3. **the same numbers show up in last year's client documents** - a lookup in documents
   the firm already has

**The finding that matters.** Part 3 is not a similarity judgement. It is *evidence*, and
it is the same kind of evidence the acceptance rule already turns on: not "these labels
look alike" but "last year's document says 412,300 against this label, and so does this
year's model". That makes the whole test **deterministic** - no model call, no embedding,
no confidence score. For repeat clients, line-item matching may need no model at all.

Three things follow.

1. **It is cheaper, faster and auditable**, and it fits "the data needs to be 100% accurate
   every time" far better than a probability would. It also matches what the harness
   literature found across eleven production systems: deterministic retrieval, no vector
   search.
2. **It is a different skill from `line-item-tagging`.** That one asks a model to tag a
   line against the firm's chart of accounts. This asks whether a line is the same line as
   last year - against the prior workbook, which the fourth session already called the real
   chart of accounts for repeat clients.
3. **`prior_model` is not enough.** P79 stores the path to last year's *workbook*. Part 3
   needs last year's *client documents* as well. Nothing in the build points at those.

**Queued as the next question**, because it decides whether part 3 is buildable at all.

## Q8 - Can the tool get to last year's client documents?

*Asked because the third part of his matching test depends on them, and nothing in the
build points at them - P79 stores the path to last year's workbook and nothing more.*

**Answer.** "Yes they are sitting in a box folder it can be pointed at."

**What this settles.** Part 3 of the matching test is buildable. Last year's source
documents are reachable the same way last year's model is: a folder a person points the
engagement at, once, at setup.

**What it means for the build.** A second pointer beside `prior_model` - call it the prior
engagement's document folder - set at `/admin`, checked when it is set rather than when a
run needs it, and refused with the same care: a path that is not there, a web link pasted
instead of a synced folder. P79 built exactly that machinery for the first pointer and it
generalises; `needs_a_prior_model()` already answers "repeat client, and do we have it".

The engagement profile is the natural home, and both pointers say the same thing in two
parts: *for a repeat client, last year is evidence, and here is where it lives.*

## Q9 - What makes an amount *not* in the ballpark?

*Asked because the build's rule is not to invent a threshold nobody set, and a wrong
number here does not fail loudly - it matches a line to the wrong row and every figure
downstream inherits it.*

**Answer.** "Yes mostly focus on the wording of the account and that the amount is not
absurd."

**What this settles, and it is a relief.** There is no tolerance to set.

* **Wording carries the match.** It is the primary signal, not one of two weighted ones.
* **The amount is a veto on the absurd**, not a ranking signal and not a tight band. A line
  item may legitimately move a long way in a year; what it may not do is turn into
  something of a different order.

**How to build it without inventing a number.** An odd-looking amount must not silently
break a match that the wording and last year's documents both support. So the amount check
**flags rather than vetoes**: it decides what the analyst is *shown*, never what the tool
decides on its own. That is P67's acceptance rule already - everything the evidence does
not cover is shown, all of it - and it means no threshold here can quietly be wrong,
because the worst a bad one can do is put an extra row in front of a person.

**Finding.** This removes the last thing that would have needed a practice decision before
the matching could be built. Wording is code, the documents check is a lookup, and the
amount only decides what is displayed.

## 6. Answered: the relay, and a button per appendix

**(b) is settled, and the other way from the fourth session.** Asked whether the tool
should move files or only test the connection, he answered both, and gave the reason:

> "there should be a test button for sharefile/box. Then an update button, to pull things
> from sharefile to box. I'm going to keep working on the power automate tool that does
> that automatically, pulls from sharefile to box. But want this as a backup if that
> doesn't work."

So this is **not** a reversal of the fourth session's decision. Power Automate is still the
thing that does the transfer, and it still sits outside the boundary. The relay is a
**backup he presses when the automatic one has not run** - which is a different object
from a pipeline stage, and the difference is what keeps the earlier decision intact.

The design consequence is that the hazard is not a failed copy. It is **two copiers**. The
relay must converge with Power Automate rather than fight it: copy and never move, skip on
identical content hash, surface a re-send rather than overwriting it, and report per file
what it did. Pressing Update after Power Automate already ran has to be a no-op that says
so.

**The appendices get a button each, not one Update Report button.** The reason is timing:

> "when the industry data is ready, I will press the industry update button. And it will do
> it for me, and I will have to point it to where that information will live. And like when
> the economic appendix is done and ready, I will click that button and it will update."

Each appendix's data becomes ready at its own moment, so the unit of action is the
appendix. And he points each one at its source, which makes the source a **setting** rather
than something the tool discovers - an appendix is an id, a source he points at, an anchor
in the document, and a kind. That is data, not code, and it has to stay data because the
real report has not been seen here.

### What this session's answers changed in the build

The existing ports are wrong against all of this, in three ways found by reading them:

1. **The sides are reversed.** `ports/storage/sharefile.py` is the read side and
   `ports/delivery/box.py` is the write side - the build assumed documents are read out of

2. **`BOX_ENTERPRISE_ID` is the wrong credential.** His own repo proves the working shape

3. **ShareFile cannot be authenticated from cold.** From the same repo: ShareFile's

And one invariant is in the way, correctly: the Delivery Port's contract says *no reading
of client folders* and *two inbound edges only - released artifacts, and the run manifest*.
A client document copied into Box is neither, so the relay gets its own surface rather than
widening a fence that was put there on purpose.

### Four things found on the way, none of them on the plan

1. **The two reachability scans could not see a new package.** Both took a hand-written
   list of shipped packages, and `report/` was on neither - so the checks that exist to
   catch "built and wired to nothing" were blind to a whole new package. Worse, the P82
   scan counted a package's own `__init__.py` as evidence its submodules were reached, so
   a package imported by nobody vouched for itself. Both now derive the list from the tree
   and reachability is a fixpoint.
2. **That immediately found three pre-existing defects.** The whole `orchestrate` package
   (P26's orchestrator, planner and triage) is imported by no production module at all;
   `deliver.workpaper` and `governance.chain` likewise. Recorded as B-058, B-059, B-060
   rather than wired, because where each belongs is a decision. It also corrects B-043,
   which counts `orchestrate` among six places masking is wired - it is four.
3. **A revert harness can poison Python's bytecode cache.** A same-size revert restored
   inside one filesystem tick leaves mtime and size unchanged, so the interpreter keeps
   serving the `.pyc` compiled from the *modified* source. Two tests failed against a file
   that was correct on disk. Every harness now bumps the mtime, and all six proofs were
   re-run.
4. **The report update destroyed the anchor it bound to.** It removed the whole span an
   anchor owns, including the heading - which carries the style and the bookmark. It
   worked exactly once; every later press refused with BINDING_MISSING. Found by C55,
   because pressing twice is the ordinary case.

## 8. Built for the test session he is about to run

He said he will bring redacted client documents and **no DD list**, so the tool has to
create one and then track against it. That turned B-054 from "someday" into the next two
phases.

**P94 - a request list when nobody wrote one.** P68 built the sections, the references,
the three statuses and the coverage, and deliberately left the items out: the only real
list in hand belonged to a client. That was right about that list and it left the
machinery unable to start. So there is now a starting list for valuation/non-ESOP - 45
items across the firm's seven sections, every one of them generic - carried as data, and
labelled a starting point everywhere it surfaces.

**P95 - the tracker reads the folder and updates itself.** Point it at a folder, get a
workbook. Each file classified from what can be read cheaply - filename, sheet names,
first rows, one page of a PDF - and matched to an item either by the number in its path
or by what the document turns out to be. The second is flagged as an inference, because
it is one.

The rule the whole thing rests on is not the matching. It is that a refresh preserves
everything a person wrote: notes, In Model?, Not Applicable. An update that cleared them
would mean re-entering them after every refresh, and so they would stop being entered.

**Two things worth saying about the boundary.** The redacted files must not go in
`fixtures/` - that is masked, synthetic or public, never a document a client sent, even
redacted. `inbox/` is gitignored and is the folder the sweep reads, so it replicates work
exactly. And the tracker reaches no model and no OCR engine, which a test holds: it is a
reading of a folder, not a run.

**And a design error corrected.** P93 was written as a blocking human gate - a signoff
from the work machine. Phases close in order, so it halted P94 the moment P94 was
finished. Evidence only the work machine can produce belongs in `BUILD/OPEN.md`, which is
what CLAUDE.md says it is for; the phase now closes on the owed thing being *recorded*,
and a test watches OPEN.md for the day it stops being owed.
