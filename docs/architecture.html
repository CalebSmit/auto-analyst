Chartwell / Automated Analyst — Architecture

— nodes

What this is

A blueprint for an automated analyst — a system that does the mechanical front end of deal work (DDR extraction, statement normalization, model building) and hands an analyst the judgment calls.

Skeleton for review. Nothing here is built.

◆ The three guarantees

No engagement can see another engagement's data. Every file is bound to one deal before anything reads it, precedents are retrieved only within the engagement's own scope, and the mask vault is per-engagement. Cross-client bleed is the failure that would end this project, and it is prevented by the shape of the graph rather than by care.

Every stated total is re-derived from its cited rows. A model may propose a figure and name its sources; deterministic code recomputes it, and a mismatch stops the run. That eliminates arithmetic error and invented totals — it does not by itself prove the model cited the right rows, which is what materiality review and the sampling audit are for.

Every loop is bounded and every run has a ceiling. Cost, time and iterations are declared in the plan before it executes, so the worst case is a number you can read rather than a surprise.

All three are properties of the graph's shape — which nodes exist, which edges don't, and which cycles are declared — not of a prompt anyone has to remember. The Runtime tab shows them as the assertions that enforce them.

◆ Three things you choose

Where files come from. Local folder, ShareFile, or client email. Same interface, swapped by config.

How much gets reviewed. The Checkpoint Policy moves advisory checkpoints — it can never switch off a guard that fails closed. That floor is not configurable.

Where the deliverable lands. Local folder, or Box via MCP or Client Credentials Grant.

Which projects are live. The roster decides which client folders get looked at tonight \u2014 an inactive one is unreachable, not merely skipped.

Which model each group builds into. Resolved by scope, exactly like a skill. Admin tab.

One library, many practice groups

Valuation, Consulting and Corporate Finance each bring their own skills, and Valuation alone splits into ESOP and non-ESOP, then repeat and new clients. So the library is layered: a skill is written once at the shallowest layer where it is true, and an engagement only sees what its scope resolves to — about a dozen skills, not the whole firm. The Skills tab is a live browser over it — and it has a drop folder that takes rough drafts in any state, because most skills will be written in Claude first.

Three ideas, three scopes

The graph sequences the steps. The harness wraps each one — context, reason, policy, act, verify. The loops are what happens when verification fails. They are not competing approaches; they operate at different scopes, and this design uses all three. The Runtime tab lays that out.

How you know it worked

Every run ends with a computed verdict against versioned criteria — five outcomes, not pass/fail — and every failure carries a code, an owner and what to do next. Those roll up into an analytics dashboard answering four questions: is it healthy, what should we fix, is it improving, is anything stuck. And the Run trace paints this same graph with what a run actually did — red where it broke, green where it passed, a spinning ring on the live step. Console tab.

The other six tabs

Skills — how a skill is chosen and loaded, in three tiers. Runtime — how a run actually executes: the compiled graph, the six loops, the contracts. Failure — every way this breaks, how it is caught, and how far the damage reaches. Assurance — how anyone knows it works, and who signs. Console \u2014 the live run, the analytics across all of them, and the run trace on this graph.
Admin \u2014 where somebody actually turns it on: locations, the active roster, model binding. Delivery — stack, cost, risks, and the decisions we need from you.

Status

A design to be argued with, not a running system. The nine skills and the reference datasets carry not yet built — wired into the guards correctly, domain logic still to come. Everything marked buildable now is ordinary plumbing that can start immediately, and that is the point of separating them: roughly two thirds of this map can be built and tested before a single valuation judgment is encoded.
