## Intent

TransportFailure is described in graph/execute.py as the only kind of failure a retry is for, and it is deliberately not a DiagnosticError because it is an infrastructure hiccup on its way to being either a successful second attempt or a quarantine record. All of that is true and none of it has ever run. The model door is the one place a call leaves this machine, and the adapter is the one place that knows what the SDK raises; ports sits below both graph and harness, so the type belongs to the port and the translation belongs to the adapter that has the exception in its hands.

## Tasks

- [x] TransportFailure belongs to the LLM port, which both the executor and the adapter can see
- [x] The adapter raises it for what a second attempt might fix, and for nothing else
- [x] A permanent failure still ends the step rather than being retried

## Exit criteria

*The phase closes when all of these are true and `gate close` says so.*

- A connection error, a timeout, a rate limit and a server error each arrive at the executor as TransportFailure
- A bad request, an unknown model and a missing credential are unchanged, and are not retried
- The executor retries a transport failure, emits step.transport_failed, and ends with PROCESS.TRANSPORT_EXHAUSTED when the attempts are used up
